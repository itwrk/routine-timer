### 1.3 率直な評価

**よくできている点**
- `Object.assign` によるデフォルト補完で後方互換を保つ習慣が定着している（`index.html:785-793`）。
- `esc()` によるHTMLエスケープが `innerHTML` 使用箇所でほぼ徹底されている。
- `twoTap()` による `confirm()` 代替が一貫している。
- `advanceRunClock()`（`index.html:1968`）が `Date.now()` の差分を使うため、タブ復帰時に経過時間が自己補正される。1秒 `setInterval` の欠落に耐える設計になっている。
- CSV出力に `timelineCsvEsc()`（`index.html:2364`）があり、`=+-@` 始まりの値に `'` を前置してスプレッドシートの数式インジェクションを防いでいる。

**問題がある点（食事機能に直接影響する順）**

| # | 問題 | 影響 |
|---|---|---|
| P1 | **同期がドキュメント全体の最終更新優先**。`syncPull()`（`index.html:2233`）は `D = remote` で丸ごと置換する。手動プルは `updatedAt` を見ずに**無条件で**上書きする（`index.html:2242` の比較は `auto` のときだけ） | Mac と iPhone で交互に触ると、片方の記録が消える。食事記録は「台所でiPhoneに1回だけ入れる」データなので直撃する。**最大リスク（§28-R1）** |
| P2 | **正規化処理が3箇所にコピーされている**（初期ロード `784-793` / `syncPull` `2245-2253` / `restoreAll` `2481`）。3つとも手書きで同じ内容 | 新しい配列を1箇所に足し忘れると、同期後やJSON復元後だけ `undefined` になって落ちる。食事機能で配列が3つ増えると発生確率が跳ね上がる |
| P3 | **`D.logs` の要素に `id` がない**（`index.html:2110`） | ID単位マージができない。ルーチンログだけは今後もLWWのまま |
| P4 | **実行状態 `run` がメモリのみ**。リロード・クラッシュ・iOSのタブ破棄で消える | 「画面を閉じても待機状態を復元する」は既存タイマーの再利用では**実現できない**。食事待機は別機構が必須 |
| P5 | **`run` / `timer` がグローバル単数**。同時に1つのタイマーしか回せない | 「待機中に通常ルーチンを動かせるか」は、既存タイマーを流用する限り No。別変数が必須 |
| P6 | `esc()` が `'`（シングルクォート）を変換しない（`index.html:1567`） | 現状は属性が全部ダブルクォートなので実害なし。**ただし新規コードで `title='...'` を書くと穴になる**。規約として明記が必要 |
| P7 | `renderRunCk()` の `run.ckDone` がインデックスの `Set`（`index.html:1854`）。項目削除で対応がずれる | 既存の軽微バグ。**今回は触らない** |
| P8 | 1ファイル2510行。CSS・HTML・JSが1つのファイルに同居し、検索以外の探索手段がない | 保守性の限界が近い（§8-3で判断） |


# 第2部 目的と統合方針

## 6. このアプリのプロダクト意図（再定義）

一般向けの生産性アプリではない。**「今の自分が、次に何をすればいいかを考えなくて済む」ための外部実行機能**である。

コードもこの意図と一致している:
- 実行画面（`#run`）は**全画面オーバーレイでタブバーごと覆う**。実行中は他のことを考えさせない設計。
- ステップ名 → モチベテキストの**二段読み上げ**（`loadStep()`, `index.html:1842`）。文字を読ませず音で次を示す。
- `slamIn()`（`index.html:1793`）でステップ切替時にフラッシュ+シェイク+効果音。開始コストの高さを演出で殴っている。
- 「今日だけの項目」「曜日・時間帯による表示条件」は、**今この瞬間に関係ないものを画面から消す**ための機構。

したがって食事機能も、**記録アプリではなく実行支援アプリとして作る**。

## 7. 食事機能の目的

| # | 目的 | 設計への落とし込み |
|---|---|---|
| 1 | 何を食べるか考える負担を減らす | 「前回と同じ」を**最上位の1タップ**にする。テンプレは選択肢であって入力欄ではない |
| 2 | 少ない工程で用意する | 手間レベル（何もしたくない/レンジだけ/フライパン/少し料理）でテンプレを絞る |
| 3 | 前後の状態を軽い負担で記録 | 食前は**空腹0-10の1項目だけ**が既定。眠気・ストレスは「＋詳しく」の裏 |
| 4 | 食後の「もっと食べたい」に対応 | 食後直後の欲求 → 待機 → 再評価 という**行動の流れ**として提示 |
| 5 | 身体的空腹と他の要因を区別 | 原因タグ（13種）を**任意・折りたたみ**で。強制しない |
| 6 | 自分に合う量・構成・待ち時間を見つける | 構造化された `mealSessions` として蓄積し、CSVでChatGPTへ |
| 7 | ChatGPTへ渡す | 既存タイムラインCSVへ統合 + 食事専用CSVの2本立て |
| 8 | 制限ではなく設計 | 「追加で食べる」を**常に同格の選択肢**として全画面に置く |
| 9 | 失敗ではなく観察 | XP・コンボ・ストリーク・紙吹雪・ジャックポットを**一切使わない** |
| 10 | 将来の献立・作り置き・在庫 | `foodStocks` を第2段階として予約。MVPには入れない |

## 8. 推奨する統合方法

### 8-1. 既存アプリへ統合する（結論: 統合する）

**理由**

1. **タイムラインが同居して初めて価値が出る。** 「17:30 眠い（気分）→ 18:00 食事 → 18:30 もっと食べたい8 → 18:35 まだ4」という並びが取れることが、この機能の本質。別アプリだと `localStorage` が分かれ、24hタイムラインもChatGPT用CSVも統合できない。
2. **同期をタダで手に入れられる。** `syncDataForCloud()` は `D` を丸ごと送るので、`D` に配列を足すだけで **GAS側の変更ゼロ**で Mac⇄iPhone 同期が効く（§21）。別アプリなら同期機構をもう一式作るか、GASを触ることになる。GASのソースはリポジトリに無い（§1.1）ので、GASを触るのは高リスク。
3. **バックアップ・復元も自動で乗る。** `backupAll()` は `JSON.stringify(D)` なので同上。
4. **音声・効果音・`twoTap()`・`esc()`・`toast()` がそのまま使える。** 待機終了の読み上げは `speak()` 1行。
5. **起動導線が既にある。** ホームが初期画面。食事カードを最上部に置けば **0タップで到達**。別アプリはブックマークを開き直す必要があり、「開くこと自体が負担」原則に反する。

**別アプリにすべき条件（今回は該当しない）**: 食事機能が単独で数千行になる／別人と共有する／異なる公開範囲が必要／リリースサイクルを分けたい。いずれも当てはまらない。

### 8-2. 通常ルーチンとしては扱わない（結論: 専用モデル）

食事セッションと通常ルーチンは構造が違う。

| | 通常ルーチン | 食事セッション |
|---|---|---|
| 構造 | 直線（ステップ配列を順に消化） | 分岐（待つ / 終える / 追加で食べる） |
| 時間 | 各ステップに予定秒数 | 食事時間は測るだけ。待機だけが予定時間を持つ |
| 入力 | なし（チェックだけ） | 0-10評価・タグ・品目（すべて任意） |
| 結果 | 完了率・XP・ストリーク | 構造化された観察記録。**評価しない** |
| 中断 | `endRun()` で破棄 | **破棄してはいけない**（食べた事実は残る） |
| 永続 | 不要（メモリのみ） | **必須**（待機中に画面を閉じる） |

無理にルーチン化すると:
- `D.logs` に入る → ストリーク・ヒートマップ・XPが食事に反応する → **禁止事項（§23）に真正面から違反**
- `steps[]` に 0-10 の評価値を持たせる場所がない → `memo` に文字列で埋め込む羽目になり、検索・集計・移行が不可能になる
- `syncShared()` が食事ステップにも走り、意図しない伝播が起きる

→ **食事専用のデータモデル（`D.mealSessions`）と専用画面（`scr-meal`）を持ち、タイマー・タイムライン・CSV・同期・バックアップという「接続点」だけを既存機構と共有する。**

### 8-3. 単一 index.html 構成は維持する（結論: 維持。ただし撤退線を引く）

6案の比較:

| 案 | 追加コスト | リスク | 判定 |
|---|---|---|---|
| **A. 単一ファイルのまま追加** | ほぼゼロ | 3200行前後に肥大 | **✅ 採用** |
| B. CSS・JSだけ外部ファイル化 | 小（ビルド不要・Pages対応） | `deploy.command` と「Downloadsに1枚落として差し替える」運用が壊れる。CLAUDE.md規約5に違反 | ❌ 今回は不可 |
| C. 機能単位でJS分割 | 中（`<script type="module">` 複数 or 分割） | Bと同じ運用破壊 + import順の事故 | ❌ |
| D. 食事画面だけ別HTML | 小 | `D` が分断される。同期・CSV・タイムライン統合が全部壊れる。**目的を否定する** | ❌ |
| E. 現構造のままモジュール化（IIFE + 名前空間） | 小 | グローバル128関数との共存で命名が二重管理に | △ 部分採用 |
| F. フレームワーク移行 | 特大（数十時間 + 全機能の再テスト） | 動いているものを全部作り直す。ビルド環境・npm・デプロイ手順の全変更。**得るものが保守性だけ** | ❌ |

**採用: A（単一ファイル維持）+ E の部分採用。**

具体的には:
- 食事関連のJSを **1つの連続ブロック** `/* ============ 🍽 MEAL SUPPORT ============ */` にまとめ、`/* ============ ☁️ 端末間同期 ============ */`（`index.html:2203`）の**直前**に挿入する。飛び地を作らない。
- 食事関連のCSSも **1つの連続ブロック** `/* meal support */` にまとめ、`/* tab bar */`（`index.html:211`）の直前に挿入する。
- 内部状態は `let mealState = {…}` の**単一オブジェクト**に集約し、グローバル変数を増やさない（`run` のような裸のグローバルを2つ目3つ目と生やさない）。

**撤退線（この条件を満たしたら案Bへ移行する）**
- `index.html` が **4500行を超えた**、または
- 食事以外にもう1つ「セッション型」機能（仮眠・過食衝動など）を実装することが決まった

そのときは `index.html` / `app.css` / `app.js` の3ファイルに割るだけ（ビルド不要・Pages互換・フレームワーク無し）。`deploy.command` は `git add -A` なので変更不要、CLAUDE.md規約5だけを改訂する。**フレームワーク移行は現時点で正当化できない。**

### 8-4. ナビゲーション（結論: ホームの「ひとことメモの直下」に状態依存カード。タブは増やさない）

4案の比較:

| 案 | 到達タップ数 | 常時コスト | 判定 |
|---|---|---|---|
| **ホームの上部に食事カード** | **0**（起動画面） | アイドル時1行（約48px） | **✅ 採用** |
| 新規タブを追加（5個目） | 1 | タブ幅が 4→5 分割（375pxで約67px/個）。使用頻度2〜3回/日に対して常時1/5の面積 | ❌ 第2段階で再評価 |
| 「記録」タブ内 | 2（タブ→スクロール） | なし | ❌ 遅すぎる |
| ホームのクイックアクション | 1〜2 | 既存にその概念がない | ❌ |

**決定理由**: 想定される最悪の使用状況は「食べ終わった直後、台所で片手、欲求が強い」。ここでのタップ数と迷いが機能の生死を決める。ホーム＝起動画面なので、上部カードなら**アプリを開いた瞬間に目に入る**。

#### ホーム内の正確な位置（Hal確認済み・2026-08-01）

**ひとことメモカード（`.memo-composer`）の直下、今日のチェックリスト（`#habitCard`）の直上。**

```
  🕹️ ROUTINE VOICE TIMER        🔥0日 Lv.1
  ┌────────────────────────┐
  │ 📝 ひとことメモ          │   ← 最上部は従来どおりメモ
  │ 🌡️ 今の気分              │
  └────────────────────────┘
  ┌────────────────────────┐
  │ 🍽 食事  [前回と同じ][選ぶ]│   ← ★ここ（アイドル時1行・約48px）
  └────────────────────────┘
  ┌────────────────────────┐
  │ ✅ 今日のチェックリスト   │
  └────────────────────────┘
  ルーチン一覧 / 今後の予定 / 24hタイムライン
```

**なぜ「メモの下」か**: Halの指定。ひとことメモは1日に何度も使う入口であり、最上部を明け渡さない。

**なぜ「チェックリストの上」か**: `#habitCard` は項目数で高さが変動する（1項目あたり約33px + 手順メモ展開）。食事カードをその下に置くと、チェック項目が増えた日にファーストビューから外れる。メモカードは高さがほぼ一定（約290px上限：入力48px + 気分2段 + 直近メモ3件）なので、その直下なら **iPhone 13 mini（可視高さ約650px）でも常にスクロールなしで見える**。

**カードは状態依存で姿を変える**（詳細は §12）:
- 未実施: 1行（`🍽 食事` ＋ `[前回と同じ]` `[選ぶ]`）
- 食事中: 経過時間 ＋ `[🍽 食べ終わった]` の大ボタン
- 待機中: 残り時間 ＋ 3ボタン
- 待機後: 再評価の入口

さらに **待機中だけ、画面下部に固定の待機バー（z=110）** を出す。これでルーチン実行中（`#run`）や設定画面からでも待機に戻れる。

**チェックリストが1行分下がる件**: 許容する。アイドル時の食事カードは48px。食事カードが大きくなるのは実際に食事セッション中だけで、そのときは食事が最優先。

## 8-A. 採用しない案と理由（まとめ）

| 採用しない案 | 理由 |
|---|---|
| 食事を別アプリにする | タイムライン統合・同期・CSVという価値の中核が失われる。GASソースが手元に無いので同期の作り直しは高リスク |
| 食事セッションを `D.routines` / `D.logs` として表現する | XP・ストリーク・ヒートマップが食事に反応し、禁止事項に違反。構造化された評価値の置き場がない |
| 既存 `run` / `timer` / `tick()` を待機タイマーに流用する | 単数グローバルなので待機中にルーチンを回せない。`run` は永続化されず、画面を閉じたら復元できない |
| 何でも入る汎用 `D.events[]` に食事も入れる | 検索・集計・移行が不可能。ChatGPTに渡すCSVも意味を持たなくなる |
| イベントソーシング（全操作をイベントとして記録し畳み込む） | 個人用アプリに対して過剰。デバッグ不能になる |
| フレームワーク移行 / npm導入 | 費用が数十時間、リスクが「全機能の再検証」。得るのは保守性のみ |
| MVPで同期機構を全面改修する | 影響範囲が全機能に及ぶ。食事の新規3配列だけID単位マージすれば実害は防げる（§21） |
| MVPでカロリー・PFC・体重・食品DB | 「数値管理しすぎない」原則に違反。かつ MVP を確実に遅らせる |
| 追加で食べなかったらXP / 我慢ストリーク | **明示的な禁止事項**。設計上ありえない |
| 食事ログを Claude API に送って助言を生成 | 公開リポジトリの直叩き実装（`aiCall()`）で食行動データを外部送信することになる。MVPでは行わない（§23） |
| 食事完了を Notion / Googleカレンダーへ自動送信 | `calLog:'auto'` を入れている端末で、食事が勝手にカレンダーに載る。MVPでは接続しない（§23） |

```
MealTemplate  ──選ばれる──▶  MealSession  ──0..n──▶  Wait
```

### 9.3 状態機械（MealSession）

```
        [なし]
          │ 食事をはじめる
          ▼
      ┌────────┐   食べ終わった    ┌─────────────┐
      │ eating │ ─────────────▶ │ afterMeal入力 │
      └────────┘                └─────────────┘
          │                        │        │
          │ 6時間放置              │待つ    │終える／追加で食べる
          │ → 確定を提案            ▼        ▼
          │                  ┌─────────┐  ┌────────┐
          │                  │ waiting │  │ closed │
          │                  └─────────┘  └────────┘
          │                        │  ▲        ▲
          │      時間到達／手動終了  │  │さらに待つ│
          │                        ▼  │        │
          │                  ┌──────────┐      │
          └─────────────────▶│afterWait │──────┘
                             │  入力    │  終える／追加で食べる
                             └──────────┘
```

**不変条件**
- 同時に `status !== 'closed'` のセッションは**最大1つ**。開始時に既存のアクティブセッションがあれば、それを先に確定させるか継続するかを聞く。
- `closed` になったセッションは削除されない（論理削除 `deletedAt` のみ）。
- どの状態からでも `[このまま終える]` と `[追加で食べる]` が選べる。**行き止まりを作らない。**

## 11. 主要ユーザーフロー

### フローA: 食事を始める（目標 1〜2タップ）

```
ホーム（起動直後）
  └ #mealCard の [前回と同じ] を1タップ
       └ セッション作成（status:'eating', startedAt=now,
          直近closedセッションの label/items/effortLevel を複製）
       └ カードが「食事中」表示に変わる。画面遷移すらしない
       └ toast「🍽 食事をはじめました」

  または [選ぶ] → scr-meal
       ├ テンプレ一覧をタップ → 開始
       └ [✏️ 自由入力ではじめる] → 1行のテキスト入力 → 開始
            （テンプレを作らなくても、その場の食事を始められる）
       └ 「食前の状態を記録（任意）」は開始後に折りたたみで出す（開始を止めない）
```

**設計上の要点**
- 食前状態の入力は**開始のブロッカーにしない**。まず開始（＝時刻の記録）を確定させ、入力は「食べながらでも、あとからでもいい」ものとして下に置く。
- テンプレ一覧の並びは `useCount` 降順 → `builtin` は最後。よく使うものが自然に上に来る。手間レベルによる絞り込みは第2段階（テンプレが4〜6件のうちは絞る価値がない）。

### フローA': テンプレを自分で増やす（3つの入口・すべて任意）

「先にテンプレを整備してから使う」を要求しない。**使った結果からテンプレが増える**設計にする。

```
① 履歴から（いちばん軽い・推奨）
   scr-meal の「最近の食事」の各行に [＋テンプレに保存]
   → その食事の label/items/effortLevel をそのままテンプレ化。入力ゼロ・1タップ
   → 既に同名テンプレがあれば「登録済みです」で何もしない

② 自由入力で始めた食事から
   自由入力で開始 → 食事中カードに [＋この食事をテンプレに保存]
   → ①と同じ処理

③ 記録タブでゼロから
   🗂️記録 → 🍽 食事テンプレを管理 → 名前を入れて [＋ 追加]
   → 追加後に「✏️ 編集」で絵文字・品目・手間レベルを設定
   （既存のチェックリスト項目管理と完全に同じ操作感）
```

**同梱の汎用テンプレ4件は消せる**（`builtin` でも削除可）。ただし削除も論理削除なので、同期で復活しない。

### フローB: 食べ終わった

```
[🍽 食べ終わった] タップ
  └ endedAt = now, status は 'eating' のまま afterMeal 入力へ
  └ 画面に「いま、もっと食べたい気持ちは？」+ 0〜10ボタン（11個・2段）
       │
       ├ 0〜3 を選択 → 「記録しました。おつかれさま。」+ [終える] [それでも少し待つ]
       │                 → [終える] で status:'closed'
       │
       └ 4〜10 を選択 → 待機の提案（下記）
```

**待機提案の文面（強制しない）**
> 食事はここまで。
> 水かお茶を飲んで、5分後にもう一度きいてみますか？

ボタン: `[5分待つ]` `[10分待つ]` `[いまは終える]` `[追加で食べる]`
→ **4つが同じ大きさ**。「追加で食べる」を小さくしたり隅に置いたりしない。

### フローC: 待機中

```
status:'waiting', waits.push({plannedSec, startedAt, endsAt: now + plannedSec*1000})
  └ #mealWaitBar が全画面に出る（ホームでもルーチン実行中でも）
  └ 表示: 「⏳ あと 4:12」
  └ ボタン: [💧水を飲んだ] [🍽 片づけた] [✅ もう落ち着いた] [🍚 まだ食べたい]
       ├ 水/片づけ → waits[last].actions に追記。バーは消えない
       ├ もう落ち着いた → 待機を手動終了 → afterWait 入力へ
       └ まだ食べたい → 待機を手動終了 → afterWait 入力へ（追加を選びやすい配置）

時間到達
  └ poan() + speak('5分たちました。いま、どのくらい食べたい気持ちですか。')
     ※ルーチン実行中（run が非nil かつ非paused）のときは読み上げを抑止し、音とバーの点滅のみ
  └ バーが「⏳ 時間になりました → [答える]」に変わる
```

**通常ルーチンとの併走**: 可能。待機タイマーは `mealState.waitTimer`（`run`/`timer` とは別）で回す。競合時の調停ルールは §18.4。

### フローD: 待機後

```
「いま、どのくらい食べたい？」0〜10ボタン（前回値を薄く表示: 「さっきは 8」）
  ↓
結果を1つ選ぶ（大ボタン・横2列）
  [😌 落ち着いた] [🙂 少し落ち着いた] [😐 変わらない] [😖 強くなった]
  ↓
  ├ 落ち着いた／少し → 「記録しました。今回はこうだった、でOK。」[終える]
  └ 変わらない／強くなった →
      「10分たっても続くなら、身体が必要としているのかも。
       追加で食べる・次回の量を増やす、どちらも記録できます。」
      [🍚 追加で食べる] [📝 次回は少し増やす] [⏳ もう5分待つ] [終える]

[追加で食べる] → extra.ate=true, extra.when='after_wait'
  └ 「何を足した？（任意）」チップ: 鶏胸肉 / 野菜 / めかぶ / ゆで卵 / 主食 / その他
  └ 選ばなくても [記録して終える] で完了できる

最後に必ず（折りたたみ・任意）
  「なぜそう感じたか、思い当たるものがあれば（任意・複数可）」
   ▸ 開くと13個のタグチップ
```

### フローE: 振り返り

`scr-meal` の下部「最近の食事」。既定は**直近10件の一覧のみ**。

```
8/1 18:02  鶏胸肉＋主食＋ほうれん草   食後8 → 5分 → 4  追加なし
7/31 12:40 買ってきた食事            食後3              追加なし
7/30 19:15 軽めの食事                食後9 → 10分 → 8  追加あり（ゆで卵）
```

**傾向表示は第2段階**。かつ以下の制約を守る:
- **セッション10件未満では傾向を一切出さない。** 代わりに「記録が10件たまると、ここに傾向が出ます（あと4件）」と表示。
- 断定しない語尾に固定: 「〜の傾向がありました」「〜が多かったです」。「〜だからです」「〜すべきです」は使わない。
- 良し悪しの判定をしない。件数と比率だけを示す。

## 14. データモデル

`D` に**4つのキー**を追加する（第2段階でもう1つ）。

```jsonc
{
  "schemaVersion": 2,          // number  必須  ★新規（既存データは 1 とみなす）
  "mealSessions": [ … ],       // MealSession[]  必須（空配列可）
  "mealTemplates": [ … ],      // MealTemplate[] 必須（空配列可）
  "foodRules": [ … ],          // FoodRule[]     必須（空配列可）
  "mealPrefs": { … },          // MealPrefs      必須
  "foodStocks": [ … ]          // 第2段階。MVPでは追加しない
}
```

### 14.1 MealSession

| フィールド | 型 | 必須 | 意味 |
|---|---|---|---|
| `id` | string | ✅ | `uid()` 生成。同期マージのキー |
| `startedAt` | number(ms) | ✅ | 食事を開始した時刻。**自動取得** |
| `endedAt` | number(ms) \| null | ✅ | 「食べ終わった」を押した時刻。**自動取得** |
| `updatedAt` | number(ms) | ✅ | このセッションを最後に触った時刻。**マージの勝敗判定に使う** |
| `deletedAt` | number(ms) \| null | ✅ | 論理削除。表示・集計・CSVから除外。60日経過で物理削除 |
| `status` | `'eating'`\|`'waiting'`\|`'closed'` | ✅ | §9.3 の状態 |
| `label` | string(≤60) | ✅ | 表示名のスナップショット。テンプレ名を複製して保持（テンプレを消しても履歴が壊れない） |
| `templateId` | string \| null | ✅ | 由来テンプレ。削除済みでも文字列は残す |
| `items` | Item[] | ✅ | 空配列可。`{name: string(≤40), amount: string(≤20)}` |
| `effortLevel` | `'none'`\|`'microwave'`\|`'pan'`\|`'cook'`\|`''` | ✅ | 手間レベル。`''` = 未指定 |
| `before` | Before \| null | ✅ | 食前の状態。未入力なら `null` |
| `afterMeal` | AfterMeal \| null | ✅ | 食後直後。未入力なら `null` |
| `waits` | Wait[] | ✅ | 空配列可。0回以上 |
| `afterWait` | AfterWait \| null | ✅ | 最後の待機後の再評価 |
| `extra` | Extra \| null | ✅ | 追加で食べたか |
| `note` | string(≤280) | ✅ | 自由記述。空文字可 |

### 14.3 FoodRule（自分ルール）

| フィールド | 型 | 必須 | 意味 |
|---|---|---|---|
| `id` | string | ✅ | |

| フィールド | 型 | 既定 | 意味 |
|---|---|---|---|
| `defaultWaitSec` | number | `300` | 待機の既定秒数 |

## 15. 各フィールドの必須・任意の考え方

- **「必須」= オブジェクトに常にキーが存在する**（値が `null` や `''` や `[]` でもよい）。理由: `Object.assign` によるデフォルト補完と、`undefined` 起因のクラッシュ防止。
- **「ユーザーの入力が必須」なものは1つもない。** 開始（`startedAt`）と終了（`endedAt`）は自動取得。それ以外はすべてスキップ可能。
- **数値評価は `0-10` の整数 または `null`。** `0` と「未入力」を区別できるようにする（`0` は「まったく食べたくない」という意味のあるデータ）。`Number.isInteger(v) && v>=0 && v<=10` で検証し、外れたら `null`。
- **時刻はすべて `number`（epoch ms）**。既存の `personalNotes.createdAt` / `moodLogs.createdAt` と同じ形式。`date`/`time` 文字列は使わない（`habitLogs` の二重表現は既存の負債であり、真似しない）。

### 17.1 現状の移行パターン（踏襲する）

既存コードは3つのやり方が混在している:

### 17.2 導入するもの

**(a) `D.schemaVersion`（number）を新設。**
- 既存データには存在しない → 読み込み時に `1` とみなす。

**(b) 正規化を1関数に集約する（P2の解消）。**

```js
  d.todayTasks     = Array.isArray(d.todayTasks)     ? d.todayTasks     : [];
  d.todayTaskLogs  = Array.isArray(d.todayTaskLogs)  ? d.todayTaskLogs  : [];
  d.logs           = Array.isArray(d.logs)           ? d.logs           : [];

  d.hitokoto       = Array.isArray(d.hitokoto)       ? d.hitokoto       : [];

  const from = Number(d.schemaVersion) || 1;
```

## 18. タイマー再利用方針

### 18.1 結論: `run` / `timer` / `tick()` は再利用しない

理由（§8-2 の再掲 + 具体）:
- `timer` は `setInterval` の単一ハンドル（`index.html:1779`）。`startRun()` が上書きする。
- `run` は永続化されない。要求「ページを閉じても待機状態を復元する」を満たせない。
- `tick()` は `run.r.steps[run.idx]` に強く依存し、ステップ概念のない待機には合わない。

### 18.2 再利用するもの

| 既存 | 用途 |
|---|---|
| `speak(text, cb)` | 待機終了の読み上げ |
| `poan(freq, dur, vol)` | 待機終了の音（`beep` より角がない。`sfxDone()` は「達成」の意味が付くので使わない） |
| `toast(msg)` | 各種フィードバック |
| `twoTap(btn, label, fn)` | セッション削除の確認 |
| `esc(s)` | すべての自由入力の描画 |
| `save()` | 保存 + 自動プッシュ |
| `activityTimeLabel(stamp)` | 「今日 18:32」形式 |
| `localDateKey(d)` | 日付キー |
| `timelineCsvEsc(v)` / `csvEsc(v)` / `download()` | CSV出力 |
| `showScreen(id)` | 画面遷移 |
| `@media (prefers-reduced-motion:reduce)`（`index.html:32`） | 自動で効く |

### 18.3 待機タイマーの設計

```js
let mealState = {
  waitTimer: null,      // setInterval ハンドル（run/timer とは完全に別）
  activeId: null,       // 進行中セッションの id（キャッシュ）
  view: 'idle'          // 'idle'|'eating'|'afterMeal'|'waiting'|'afterWait'|'extra'
};
```

**原則: 経過時間を積み上げない。常に `endsAt - Date.now()` で計算する。**

```js
function mealWaitRemainMs(){
  const w = activeWait();                       // waits[waits.length-1]
  return w ? Math.max(0, w.endsAt - Date.now()) : 0;
}
function startMealWaitTimer(){
  stopMealWaitTimer();
  mealWaitTick();                                // 即座に1回
  mealState.waitTimer = setInterval(mealWaitTick, 1000);
}
function mealWaitTick(){
  const ms = mealWaitRemainMs();
  renderMealWaitBar(ms);
  if(ms <= 0) onMealWaitFinished();
}
```

**iOS のバックグラウンド対策**（`setInterval` は画面ロック中に止まる）:

```js
document.addEventListener('visibilitychange', ()=>{ if(!document.hidden) resumeMealWait(); });
window.addEventListener('focus',   resumeMealWait);
window.addEventListener('pageshow', resumeMealWait);   // iOS の bfcache 復帰
```
`resumeMealWait()` は「アクティブな待機があれば `mealWaitTick()` を即実行し、必要なら `setInterval` を張り直す」だけ。`endsAt` が絶対時刻なので、何秒止まっていても正しい残り時間になる。

**復元（起動時）**

| 復元時の状態 | 挙動 |
|---|---|
| `status:'waiting'` かつ `endsAt > now` | 待機バーを出して継続。残り時間は再計算 |
| `status:'waiting'` かつ `endsAt <= now` | 「⏳ 待機時間は終わっています」+ `[答える]`。**音と読み上げは鳴らさない**（何時間も前かもしれないため） |
| `status:'eating'` かつ `startedAt` が6時間以上前 | 「〇時間前の食事がまだ記録の途中です。このまま記録を終えますか？」`[記録を終える][続きを入力する]` |
| `status:'eating'` かつ6時間以内 | そのまま継続表示 |

### 18.4 複数タイマーの競合ルール

| 状況 | 挙動 |
|---|---|
| ルーチン実行中に待機開始 | **許可する。** 待機バー(z=110)が `#run` の上に出る |
| 待機中にルーチン開始 | **許可する。** 待機は継続 |
| 待機終了 かつ `run !== null && !run.paused` | **読み上げを抑止**（ルーチン読み上げと衝突するため）。`poan()` とバーの点滅・`toast()` のみ |
| 待機終了 かつ `#result.show` が表示中 | 音のみ。バーは `#result` の下に隠れるが、閉じれば見える |
| 待機中に別の食事セッションを開始しようとした | `[先の食事を終える] [続ける]` を提示。**アクティブは常に最大1つ** |
| 待機中に `endRun()`（ルーチン中断） | 待機は無関係に継続する |
| 待機中に `resetAll()` | 全データが消える。既存の破壊的操作なので `twoTap` のまま。追加の保護はしない |

## 21. 同期・競合への対応

### 21.1 GASは変更しない（できない）

`syncDataForCloud()`（`index.html:2224`）は `D` を丸ごとディープコピーして送る。したがって **`D.mealSessions` などを足すだけで、GAS側の変更ゼロでクラウド保存される。** GASソースがリポジトリに無い（§1.1）ことを踏まえると、これは統合案の決定的な利点。

**確認事項**: `syncPush` のペイロードサイズ。`mealSessions` 1000件 × 約700バイト ≒ 700KB。既存の `D` も含めると 1MB を超える可能性がある。Apps Script の `doPost` は POST ボディ最大約50MBなので技術的には通るが、iPhone のモバイル回線で4秒デバウンスごとに1MB送るのは実用的でない。

→ **対策**: 上限を `mealSessions` 1000件に設定（§17.4）。加えて、`syncPush` の前に `JSON.stringify(payload).length` を測り、**2MBを超えたら警告トーストを出す**（送信自体は行う）。実装は3行。閾値超過が常態化したら、そのときに差分同期を検討する。

### 21.2 競合対策: 新規3配列だけID単位マージ

`syncPull()` で `D = remote` する**直前**に、食事の3配列をマージする。

```js
const MERGE_COLLECTIONS = ['mealSessions','mealTemplates','foodRules'];

function mergeMealCollections(local, remote){
  for(const k of MERGE_COLLECTIONS){
    const l = Array.isArray(local[k])  ? local[k]  : [];
    const r = Array.isArray(remote[k]) ? remote[k] : [];
    const map = new Map();
    for(const it of r) if(it && it.id) map.set(it.id, it);
    for(const it of l){
      if(!it || !it.id) continue;
      const prev = map.get(it.id);
      if(!prev){ map.set(it.id, it); continue; }
      // updatedAt が新しい方を採用。同値ならリモート優先（決定的にする）
      if((Number(it.updatedAt)||0) > (Number(prev.updatedAt)||0)) map.set(it.id, it);
    }
    remote[k] = [...map.values()];
  }
}
```

**tombstone を配列に残す理由**: 削除済みレコードを配列から消してしまうと、もう一方の端末がまだ持っている生きたレコードとマージされて**復活する**。したがって `deletedAt` を立てた「墓標」を配列に残し、表示・集計・CSVの各所で `filter(x => !x.deletedAt)` する。60日で物理削除（§17.4）。

**削除処理は必ず論理削除にする**:
```js
// ❌ D.mealSessions = D.mealSessions.filter(s => s.id !== id);
// ✅
const s = D.mealSessions.find(x => x.id === id);
if(s){ s.deletedAt = Date.now(); s.updatedAt = s.deletedAt; s.note = ''; s.items = []; }
```

### 21.3 手動プルの保護

現状 `syncPull()`（引数なし）は `updatedAt` を無視して無条件に上書きする（`index.html:2242`）。これは「⬇️ 今すぐ取得」を押しただけでローカルの新しい記録が消える動作。

→ **`remote.updatedAt < D.updatedAt` のとき、`twoTap()` による2度押し確認にする。**
文言: `⚠️ クラウドの方が古いです。もう一度で上書き`

3行の変更で、最も痛い事故を防げる。

### 21.4 やらないこと（MVP）

| 項目 | 判断 |
|---|---|
| `personalNotes` / `moodLogs` / `habitLogs` / `todayTaskLogs` のID単位マージ | **第2段階。** 既存の挙動を変えるとリグレッション範囲が全機能に及ぶ |
| `D.logs` のマージ | **第2段階。** 要素に `id` がない（P3）。まず `id` の付与から必要 |
| 差分同期 / オペレーションログ | **やらない。** 個人用アプリに対して過剰 |
| GAS側でのマージ | **やらない。** ソースが手元になく、デプロイ事故のリスクが大きい |

**正直な限界の明示**: この設計で守れるのは食事データだけである。メモ・気分・チェック・ルーチンログは今日と同じく最終更新優先で、端末をまたぐと消えることがある。これは既存の問題であり、食事機能が悪化させるものではない。第2段階で同じ `mergeCollections` を横展開すれば解消できる（`D.logs` を除く）。

# 第6部 プライバシーと安全性

## 23. プライバシー

### 23-1. リポジトリが公開されていることの帰結

| 守ること | 実装上の要求 |
|---|---|
| 食事ログ・個人メモをソースに埋め込まない | `mealSessions` の初期値は**必ず `[]`**。テストデータをコミットしない |
| 同期合言葉を埋め込まない | `PRESET_SYNC.key` は `''` のまま（`index.html:798`）。食事機能は同期設定に一切触らない |
| APIキーをGitに保存しない | 食事機能は `settings.apiKey` を読まない・書かない |

### 23-2. Google Drive へ送られるデータ（明示）

`syncPush()` が送るもの:
1. `syncDataForCloud()` = **`D` 全体から `settings.apiKey` / `syncUrl` / `syncKey` / `autoSync` を除いたもの**
   → 食事機能追加後は、**食事の全記録（品目名・数値評価・原因タグ・自由記述メモを含む）がここに入る**。
2. `routine_timeline.csv`（ChatGPT用CSVの中身）
   → `mealPrefs.includeInChatGptCsv` が真なら食事行も入る。

保存先はユーザー自身のGoogle Drive内の `rvt_sync.json`（およびCSVファイル）。第三者のサーバーは経由しない。ただし **GASウェブアプリのURLを知り、かつ合言葉を知っている人は読める**。

→ **設定画面の同期カードに一文を追加する**:
> ☁️ 同期をONにすると、食事の記録（内容・数値・タグ・メモ）もGoogle Driveに保存されます。

### 23-3. 個人の食事テンプレートをコミットするリスク

「鶏胸肉100〜130g / 冷凍ほうれん草 / めかぶ / トマトジュース」を `PRESET_STEPS` のようにコード同梱すると:
- 公開リポジトリに**利用者の食生活の具体像が永久にコミットログとして残る**。あとで消してもgit履歴からは消えない。
- 「Halの食事内容」という、本人にしか関係ない情報が検索可能になる。

→ **同梱するのは汎用テンプレ4件のみ**（買ってきた食事 / 軽めの食事 / 温めるだけの食事 / 自由入力）。個人テンプレは `scr-meal` の `[ 定番の食事をつくる ]` ボタンでローカル生成する。生成されたテンプレは `D` に入るので同期・バックアップには乗るが、**Gitには入らない**。

### 23-4. ChatGPT用CSVの項目選択

設定画面の食事カードにトグルを3つ:
- `食事の記録をChatGPT用CSVに含める`（`includeInChatGptCsv`、既定ON）
- `品目名も含める`（`csvIncludeItems`、既定ON）
- `自由記述メモも含める`（`csvIncludeNotes`、既定ON）

「何を食べたか」は共有したいが「そのとき何を思ったか」は共有したくない、という分離ができる。

### 23-5. 外部送信の禁止事項（実装規約）

| 送信先 | 食事データ |
|---|---|
| `api.anthropic.com`（`aiCall()`, `index.html:968`） | **送らない。** MVPで食事にAI機能は付けない |
| Notion Webhook（`sendNotion()`, `index.html:2082`） | **送らない。** `finishRun()` からしか呼ばれないので、食事側から呼ばなければ自動的に守られる |
| Googleカレンダー（`calAddEvent()`, `index.html:2309`） | **送らない。** `calLog:'auto'` の端末で食事が勝手にカレンダーに載るのを防ぐ |

第2段階以降でこれらを検討する場合も、**既定OFFの明示的なトグルを必須**とする。

### 23-6. 削除方法

| 単位 | 方法 |
|---|---|
| 1セッション | 履歴の各行 → `twoTap()` で論理削除（`deletedAt`） |
| 全食事データ | 設定の食事カード → `[食事データだけ削除]` を `twoTap()` で。`mealSessions` を全件 tombstone 化。テンプレとルールは残す |
| 全部 | 既存の `[全データ初期化]`（`resetAll()`） |

**tombstone にした時点で `items` / `note` / `tags` を空にする**（§21.2）。墓標にはIDと `deletedAt` しか残らないので、削除後のデータがクラウドに残り続けることはない。

### 23-7. 心理的安全性（ゲーミフィケーションからの隔離）

**ハード制約。実装レビューで機械的に確認する。**

| 禁止 | 確認方法 |
|---|---|
| 食事に関連して `D.xp` を増減させる | 食事ブロック内に `D.xp` が出現しないこと |
| 食事に関連して `D.combo` を触る | 同上 `D.combo` |
| 食事を `D.logs` に入れる | 同上 `D.logs.unshift` / `D.logs.push` |
| ストリーク・ヒートマップに食事を反映 | `streak()` / `renderProg()` を変更しないこと |
| `confetti()` / `burst()` / `sfxJackpot()` / `slamIn()` / `xpPop()` / `jackpot()` を食事で呼ぶ | 食事ブロック内にこれらが出現しないこと |
| `sfxDone()` を食事で呼ぶ | 「達成」の意味が付いているため。`poan()` を使う |
| 「我慢できた/できなかった」「成功/失敗」等の語 | §13 の禁止語リストを grep |

**「追加で食べた」は減点ではなく、ただのデータ。** UIでも赤・警告色を使わず、他の選択肢と同じ配色にする。

## 24. MVP

ユーザー提示の15項目を再評価した結果:

### 採用（そのまま）

1. ホームから食事サポートを開く（→ ホーム最上部カード。0タップで視認）
2. 食事テンプレ・前回・自由入力から選ぶ（→ **「前回と同じ」を最上位**に格上げ）
4. 食事終了を記録
5. 食後直後の追加欲求を0〜10で記録
6. 5分・10分待機タイマー
7. 水を飲んだなどの簡単な記録
8. 待機後の追加欲求を記録
9. 追加で食べたかを記録
10. 食事セッションを保存
11. 履歴を確認（**一覧のみ。傾向表示なし**）
12. 24時間タイムラインへ簡略表示
13. ChatGPT用CSVへ出力（**＋ 食事専用CSVも追加**）
14. GAS同期とJSONバックアップに含める
15. ページを閉じても待機状態を復元する

### 縮小して採用

3. **食事前の状態は任意入力** → 既定は**空腹の1項目だけ**。眠気・ストレスは「＋詳しく」の裏に格納。
   理由: 食事の前に3項目を入力させると、その時点で「アプリを開く負担」が発生し、機能が使われなくなる。空腹だけあれば「食後の欲求8」が解釈可能になる。

### 追加（提示リストにないが必要）

16. **原因タグ13種**（折りたたみ・任意・複数選択）
   理由: 「身体的空腹とストレスを区別する」は目的の中核（§7-5）。データが無ければ第2段階の振り返りが空虚になる。実装コストは小さい。
17. **自分ルール（`foodRules`）の表示と手動追加**
   理由: 「今の自分が次に何をすればいいか」を出す最小の仕組み。「まず水を1杯」という1行が、傾向分析より先に効く。
18. **中断・放置セッションの復帰処理**
   理由: 「食べ終わった」を押し忘れる日が必ずある。放置セッションが1件でも残ると、翌日の「前回と同じ」が壊れる。
19. **`normalizeData()` への正規化統合（先行コミット）**
   理由: §1.3-P2。これを先に入れないと、食事の3配列を同期・復元経路に足し忘れる事故が起きる。
20. **テンプレを自分で増やせる3つの入口**（フローA'・Hal要望 2026-08-01）
   ・履歴の各行から `[＋テンプレに保存]`（入力ゼロ・1タップ）
   ・`✏️ 自由入力ではじめる`（テンプレを作らずに食事を始められる）
   ・記録タブでの追加・編集・削除
   理由: 「先にテンプレを整備してから使う」を前提にすると、整備自体が開始コストになって機能が使われない。**使った結果からテンプレが増える**形にする。3つとも実装コストは小さい。

### MVPから除外（提示どおり）

カロリー計算 / 栄養データベース / 体重管理 / 写真認識 / AIによる自動献立 / 高度な統計 / 賞味期限通知 / バーコード / 買い物リスト / 完全な冷凍庫管理

### MVPから除外（追加で判断）

| 項目 | 理由 |
|---|---|
| 傾向表示（フローE の分析） | 記録が10件たまるまで意味を持たない。**先にデータを溜める**のが正しい順序 |
| 食事の後付け記録（過去の食事を手動で足す） | 「今の行動を助ける」が中心。過去の入力は負担にしかならない |
| テンプレの手間レベル絞り込み | テンプレが4〜6件のうちは絞り込む価値がない。第2段階 |
| 食事のインポート（CSV） | 出力だけで足りる |
| `personalNotes` などのマージ同期 | §21.4 |
